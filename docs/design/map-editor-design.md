# 招新考核地图编辑器设计

## 1. 文档目的

本文档定义招新考核平台中“题目编排编辑器”模块的第一版设计基线，供后续成员协作、拆分任务和补充方向内容使用。编辑器是平台的一个入口，不代表项目的全部边界。

第一版的产物是一套可视化地图编排工具。组织者可以通过拖拽节点、建立连线和编辑节点元数据，搭建一张可调整路线的闯关地图。本文档不定义任何具体关卡题目、任务答案或方向内容。

## 2. 产品定位

地图编辑器面向考核组织者和出题协作者，不直接面向参加考核的新生。它负责表达“考核路线如何组织”，而不是执行考核任务。

核心抽象如下：

```text
地图编排层
    ↓
关卡节点层
    ↓
独立 sandbox 引用
    ↓
未来的运行与判定系统
```

地图是可编辑的有向图。节点是相互独立的关卡单元，连线表达节点之间的转移关系。后续可以增加线性路线、分支、汇合、支线、检查点和循环，但不需要修改编辑器的核心模型。

## 3. 设计目标

第一版需要满足以下目标：

1. 可以从空白地图开始创建节点和连线。
2. 可以自由移动、删除、复制和重新组织节点。
3. 可以编辑节点的名称、说明、提示、通关条件等元数据。
4. 可以编辑连线的触发方式和分支条件描述。
5. 可以识别常见的地图结构问题，并以可读的方式提示。
6. 可以导入和导出结构稳定、适合 Git 管理的地图定义文件。
7. 可以为每个节点预留独立 sandbox 的引用，但第一版不运行 sandbox。
8. 不依赖任何具体方向或具体关卡内容。

## 4. 非目标

以下内容明确不属于第一版：

- 编写或预置 AI Infra、传统 HPC、Git、Linux 等实际关卡内容。
- 创建、启动、限制或销毁 sandbox。
- 执行测试、判题、性能测量或排行榜逻辑。
- 实现考核参与者端的闯关运行界面。
- 实现账号、权限和多人实时协同编辑。
- 实现拖拽上传代码、数据集或容器镜像。
- 通过特定方向的业务规则限制地图节点类型。

## 5. 用户工作流

第一版组织者工作流如下：

```text
新建或导入地图
    ↓
从节点面板拖入节点
    ↓
在画布中移动节点并建立连线
    ↓
在属性面板填写或修改节点元数据
    ↓
设置连线触发方式和条件描述
    ↓
运行地图结构校验
    ↓
保存或导出地图定义
```

地图可以保存为空白或半成品状态。未填写的任务内容应该显示为待补充提示，而不是阻止协作者先搭建路线。

## 6. 地图模型

### 6.1 地图文档

地图文档由地图元数据、节点集合和连线集合组成。地图语义数据与画布布局数据分开保存，避免调整布局时产生无关的内容变更。

```text
MapDocument
 ├── schemaVersion
 ├── meta
 │    ├── id
 │    ├── name
 │    ├── description
 │    └── version
 ├── nodes
 └── edges
```

地图定义文件应包含明确的 schema 版本。字段命名和序列化顺序需要保持稳定，便于代码审查和 Git diff。具体文件后缀和最终序列化格式可以在实现阶段确定，优先考虑 JSON 或 YAML。

地图语义数据与画布布局数据需要分层保存：节点的任务字段、连线规则属于语义数据，节点坐标属于布局数据。第一版可以在同一文件中使用独立的 `position` 字段表达布局，后续如有需要再拆分为单独布局文件。

### 6.2 节点

节点由稳定 ID、节点类型、元数据、sandbox 引用和画布位置组成。

```text
Node
 ├── id
 ├── type
 ├── metadata
 │    ├── title
 │    ├── directionTags
 │    ├── description
 │    ├── hints
 │    ├── completionCriteria
 │    └── retryPolicy
 ├── sandboxRef
 └── position
      ├── x
      └── y
```

第一版节点元数据只提供字段和编辑能力，不填入真实关卡内容。建议字段含义如下：

- `title`：节点在地图上的显示名称。
- `directionTags`：方向或主题标签，初始为空，可供后续分流使用。
- `description`：任务说明，支持普通文本；是否支持 Markdown 可在实现阶段确定。
- `hints`：有序提示列表，允许为空。
- `completionCriteria`：通关条件描述，允许为空或处于待补充状态。
- `retryPolicy`：重试相关设置，第一版只保存配置，不执行重试逻辑。
- `sandboxRef`：未来关联关卡目录、环境模板或运行配置的引用，第一版允许为空。

`sandboxRef` 与任务元数据分开保存，便于未来替换运行环境而不改动任务说明。

### 6.3 连线

连线单独建模，避免把转移规则隐藏在节点内部。

```text
Edge
 ├── id
 ├── source
 ├── target
 ├── trigger
 ├── condition
 └── label
```

第一版至少需要支持以下表达能力：

- 从一个节点连接到另一个节点。
- 标记连线是正常完成、失败、跳过或人工选择后触发。
- 为分支连线填写可读的条件或说明。
- 修改、删除和重新连接连线。

第一版不解释条件表达式，也不执行分支。编辑器只负责保存条件描述，并在结构层面检查连线是否合法。

### 6.4 节点类型

第一版保持最小节点类型集合：

| 类型 | 用途 |
| --- | --- |
| `Start` | 地图入口 |
| `Task` | 可关联具体任务的普通节点 |
| `Branch` | 表达路线选择或条件分支 |
| `Checkpoint` | 表达阶段检查或路线汇合 |
| `End` | 地图出口 |

AI Infra、传统 HPC、Git、Linux 等不作为写死的系统级节点类型，而通过节点元数据、方向标签和后续内容表达。

## 7. 编辑器界面

### 7.1 总体布局

```text
顶部工具栏
  地图名称 | 撤销/重做 | 保存 | 校验 | 导入/导出

左侧节点面板
  节点类型列表、搜索、拖拽入口

中间地图画布
  网格、节点、连线、缩放、平移、选择

右侧属性面板
  当前节点或连线的编辑表单

底部校验面板
  错误、警告、待补充项和定位入口
```

### 7.2 画布交互

画布需要支持：

- 拖拽创建节点。
- 拖动节点调整布局。
- 从节点端口建立和修改连线。
- 单选、多选、删除和复制节点。
- 平移、缩放和适应画布。
- 选中节点或连线后在右侧面板编辑属性。
- 撤销和重做编辑操作。

节点卡片只显示能帮助快速识别的少量信息，例如类型、标题和方向标签。完整说明、提示和通关条件放在属性面板中，避免地图被长文本填满。

### 7.3 属性面板

选中节点时，属性面板至少提供以下区域：

1. 基本信息：类型、名称、标签。
2. 任务说明：说明文本编辑区。
3. 提示：可排序的提示条目列表。
4. 通关条件：可编辑的条件条目或说明文本。
5. 运行预留：重试设置和 sandbox 引用。

选中连线时，属性面板提供：

1. 起点和终点。
2. 触发方式。
3. 分支条件或转移说明。
4. 地图上显示的连线标签。

### 7.4 空状态和编辑状态

编辑器需要明确区分以下状态：

- 空白地图：引导创建第一个节点，不出现虚构的关卡内容。
- 已选节点：显示节点属性和待补充字段。
- 已修改未保存：工具栏显示未保存状态。
- 校验失败：显示错误并支持定位到对应节点或连线。
- 导入失败：保留当前编辑内容，并展示可读的格式错误。
- 导出成功：显示文件名和 schema 版本。

## 8. 地图校验

校验分为结构错误、配置警告和内容待补充三类。空白或协作中的地图可以保存，但发布或交给运行器之前应能识别阻断性问题。

### 8.1 结构错误

- 节点 ID 重复。
- 连线 ID 重复。
- 连线引用了不存在的节点。
- 地图没有起点。
- 地图没有终点。
- 存在从起点不可达的节点。

### 8.2 配置警告

- 存在没有后继节点的非终点节点。
- 分支节点没有足够的出边（默认至少需要 2 条）。
- 分支出边缺少条件描述。
- 存在循环路径。
- 节点位置重叠或地图布局过于拥挤。

循环不在第一版中强制禁止，因为未来可能需要表达重试、回到检查点或重复挑战。默认将其作为需要确认的警告。

### 8.3 待补充项

- 节点名称为空。
- 任务说明为空。
- 通关条件为空。
- sandbox 引用为空。

待补充项不阻止保存空白地图，但应在校验面板中清楚标记。

## 9. 保存与协作

第一版采用文件优先的协作方式：


- 地图定义文件是协作和版本管理的正式产物。
- 编辑器需要支持导入和导出。
- 节点和连线使用稳定 ID，避免仅因拖动或排序导致大量 diff。
- 画布位置单独保存，内容字段和布局字段分离。
- 地图文件包含 schema 版本，便于未来迁移。
- 不把代码、数据集、容器镜像等二进制资源直接嵌入地图文件。

浏览器本地草稿可以作为便利功能，但不替代导出的地图文件，也不作为多人协作的数据源。第一版不引入登录、远程数据库和实时协同。

## 10. 视觉方向

界面参考 StyleKit 的风格组织方式，采用适合工具型产品的 Editorial 网格与 Notion/Stripe 式信息面板组合：

- 以浅色背景、深色文字和细边框建立清晰层级。
- 使用网格背景强化地图画布的空间感。
- 用少量稳定颜色区分节点类型或状态，不让颜色承担复杂语义。
- 通过排版、间距和对齐体现层级，减少装饰性渐变和大面积阴影。
- 右侧属性面板保持紧凑，但给多行文本和列表足够空间。
- 工具栏中的撤销、重做、保存、校验、导入和导出优先使用熟悉图标，并提供悬停说明。
- 颜色、字体、边框和间距应通过统一设计 token 管理，避免各节点类型自行产生视觉风格。

界面重点是让协作者快速读懂路线和修改内容，而不是营造宣传页或游戏大厅效果。

## 11. 后续扩展接口

第一版需要为后续系统保留以下接口，但不实现其运行能力：

```text
地图编辑器
    ↓ 导出 MapDocument
考核运行器
    ↓ 根据节点定位资源
SandboxAdapter
    ↓ 启动独立环境
CheckerAdapter
    ↓ 返回完成状态和结果
MapState
    ↓ 解锁后继节点
```

未来可以在不改变编辑器基本交互的情况下增加：

- 节点目录与 sandbox 资源关联。
- 节点完成判定和运行结果回写。
- 分支条件的可执行表达式。
- 参与者端地图展示。
- 方向分流和兴趣标签统计。
- 地图版本发布和多人协作。

## 12. 设计完成标准

在进入实现阶段前，以下问题应保持明确：

1. 编辑器编辑的是地图编排，不是实际关卡内容。
2. 节点和连线是独立对象，并拥有稳定 ID。
3. 节点元数据可以为空，但空字段会被标记为待补充。
4. sandbox 通过引用预留，不在第一版中启动。
5. 地图结构校验与未来的运行判定分离。
6. 导入导出文件适合放入 Git 进行协作。
7. 方向分支通过可扩展标签和节点配置表达，不写死在核心模型中。

本设计不包含具体关卡内容，后续方向负责人可以在此基线上独立补充节点资源和任务方案。

## 13. 第一版目录与资源模型

第一版采用“地图拓扑、节点资源、分类目录”三者分离的目录模型：

```text
content/
  maps/
    recruitment-map/
      map.json              # 地图元数据、节点引用、连线和画布坐标
  nodes/
    <node-id>/
      node.json             # 节点元数据；第一版可以为空白
      sandbox/              # 预留给未来的独立运行环境
  catalog/
    categories.json         # 阶段、方向和标签分类
```

分类目录只负责节点面板中的筛选和组织，不决定节点之间的连接关系。地图连线始终是路线拓扑的唯一来源，因此节点可以跨阶段、跨方向复用，也可以被多个地图引用。第一版编辑器允许在空白地图中拖入节点模板，随后把节点元数据保存到地图文档；目录结构为后续拆分为独立节点资源预留稳定 ID。

第一版的仓库骨架会提供空地图和空分类目录，不预置任何具体关卡题目、答案或方向内容。
